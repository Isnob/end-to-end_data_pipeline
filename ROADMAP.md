# Road Map: End-to-End Data Pipeline

Этот документ описывает пошаговый план развития проекта: от сбора "сырых" данных до построения профессионального аналитического хранилища с контролем качества и CI/CD.

---

## Этап 1: Инфраструктура и Ingestion (Сбор данных)
**Статус: Завершено**
**Цель:** Научиться стабильно доставать данные и упаковывать код в контейнеры.

### Что изучено:
- [x] **Библиотеки:** `ccxt` (криптовалюты).
- [x] **Валидация:** `Pydantic` для строгой проверки схем данных.
- [x] **Контейнеризация:** `Docker` и `docker-compose`.
- [x] **БД:** Основы PostgreSQL.

### Задача:
Написать Python-скрипт, который забирает данные (например, курсы BTC/USD и ETH/USD) и сохраняет их в PostgreSQL. Код должен быть полностью контейнеризирован.

### Результат:
- [x] В базе PostgreSQL копятся «сырые» данные в таблице `raw_assets`.
- [x] Проект запускается одной командой `docker-compose up`.

---

## Этап 2: Оркестрация (Управление запуском)
**Статус: В процессе**
**Цель:** Уйти от ручного запуска и перейти к автоматическому расписанию.

### Что изучить:
- [ ] **Airflow Concepts:** Архитектура (Scheduler, Worker, Webserver).
- [ ] **DAGs:** Определение графов зависимостей.
- [ ] **Operators vs TaskFlow API:** Современные способы написания тасок.
- [ ] **Scheduling:** Cron-выражения и интервалы запуска.

### Задача:
Развернуть Airflow в Docker. Переписать запуск скрипта из Этапа 1 в виде задачи (Task) внутри Airflow DAG. Настроить запуск каждые 15 минут.

### Результат:
- Автоматизированный пайплайн с логированием и обработкой ошибок.
- UI Airflow отображает успешные запуски.

---

## Этап 3: Трансформация и моделирование (dbt)
**Цель:** Научиться превращать «мусор» в чистые аналитические витрины.

### Что изучить:
- [ ] **dbt (Data Build Tool):** Основы, установка, подключение к БД.
- [ ] **Методология:** Слои Staging -> Intermediate -> Marts.
- [ ] **SQL:** Написание модульных SQL-моделей.
- [ ] **Документация:** Генерация документации через dbt.

### Задача:
Подключить dbt к PostgreSQL. Написать модели, которые:
1. Очищают данные из `raw_assets` (дедупликация, приведение типов).
2. Создают витрину `dim_assets_daily` со средними ценами за день.

### Результат:
- Чистые таблицы в базе, готовые для аналитики.
- Построенный граф зависимостей (Lineage Graph) в dbt.

---

## Этап 4: Хранилище и Скорость (OLAP)
**Цель:** Понять разницу между транзакционными (OLTP) и аналитическими (OLAP) БД.

### Что изучить:
- [ ] **ClickHouse:** Архитектура, колоночное хранение.
- [ ] **MergeTree:** Основной движок таблиц в ClickHouse.
- [ ] **Data Transfer:** Как переливать данные из Postgres в ClickHouse (через Python или плагины).

### Задача:
Добавить в `docker-compose` контейнер с ClickHouse. Настроить процесс переноса агрегированных данных (Marts) из PostgreSQL в ClickHouse.

### Результат:
- Система, способная мгновенно отдавать отчеты по миллионам строк.
- Разделение: Postgres для накопления, ClickHouse для анализа.

---

## Этап 5: Data Quality и CI/CD
**Цель:** Обеспечение надежности данных и автоматизация проверок.

### Что изучить:
- [ ] **Great Expectations:** Написание тестов для данных (Expectations).
- [ ] **GitHub Actions:** Автоматизация пайплайнов (Linting, Testing).
- [ ] **Data Contracts:** Базовое понимание контрактов данных.

### Задача:
1. Написать тесты `Great Expectations`, проверяющие, что цена (`price`) не отрицательная и нет `NULL` в ключевых полях.
2. Настроить GitHub Action, который запускает тесты dbt и линтеры при каждом `push` в репозиторий.

### Результат:
- Профессиональный репозиторий с автоматическими проверками качества.
- Гарантия того, что сломанный код не попадет в продакшн.
